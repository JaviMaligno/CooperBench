# Experiment 2: Restart vs Iterate (blog article 2)

Does a coding agent do better by **iterating** on a failing attempt (patch the
sinking ship) or by **throwing it away and restarting**? Inspired by Karpathy's
"let the loop restart". Follow-up to the CooperBench structure article
(`DESIGN.md`), reusing its harness, tiers, tooling, and rigor protocol.

## Why a new harness

Article 1 could NOT measure this: CooperBench agents make a single pass and
never see test results, so the failure signal that would prompt a restart never
reaches them (0 voluntary restarts across 1,806 mined trajectories — an
artifact of the setup, not a finding). We add the missing piece: a
**loop-with-evaluator** — attempt → run the feature's tests → show the agent
the results → next round.

Prior mining (kept as motivation, not evidence): at short horizon, destructive
commands correlate with weakness (flailing), and after *imposed* restarts
(territory reverts) the strong tier adapts while the weak one re-tries the
same file.

## Design overview

Two phases, staged with budget gates. **Hybrid**: Phase 1 measures restart as
a *policy imposed by the harness* (A/B/C); Phase 2 hands the *decision* to the
agent and measures metacognition against Phase 1's ground truth.

### Task unit and models

- Unit: a **single feature** from CooperBench flash_amd64 (no pairs — no
  collaboration here). Pool: all distinct features across its 9 tasks / 5
  repos, 29 features (exact count fixed at implementation and frozen for
  all conditions).
- Models: `azure/gpt-5.4-mini` (weak) and `azure/gpt-5.4` (strong), native
  litellm route via `azure_env.sh`, docker backend, redis on 6398.

### The loop

Each run = up to **K = 4 rounds** (1 initial attempt + up to 3 with test
feedback; stop early on success). K=4 is the minimum that can *exhibit* a
plateau (≥2 rounds without progress) and still leave room to react; the pilot
may recalibrate it. Every round has the same step/cost cap
(`MSWEA_GLOBAL_COST_LIMIT` per process), so policies compare at equal compute.

After each round the **visible evaluator** runs the feature's test suite
(reusing `run_patch_test`) and feeds back, in identical format for all
policies: pass/fail counts + truncated output of failing tests.

### Phase 1 — three imposed policies

Same features, same order, same K, same per-round caps. Only the reset rule
differs:

| policy | code between rounds | agent context between rounds |
|--------|--------------------|------------------------------|
| ITERATE | keeps its own diff | accumulates (one long trajectory) |
| RESTART-FRESH | reverted to base | fresh (no memory of prior attempts) |
| RESTART-INFORMED | reverted to base | carries a short summary of what failed |

Notes:
- "Reverted to base" = the agent's **entire diff** is dropped; the underlying
  repo is untouched (feature-scoped tasks make this the fair global restart).
- RESTART-FRESH is deliberately best-of-K sampling — that IS the Karpathy
  claim; we test it at equal compute, not apologize for it.
- FRESH vs INFORMED separates the mechanism: if INFORMED > FRESH the *lesson*
  helps; if FRESH ≥ INFORMED the contaminated context was the problem.
- The INFORMED summary is generated by the harness from round artifacts (test
  output + diff stats), NOT free-written by the failing agent, so its quality
  is uniform across rounds and tiers.

### Phase 2 — the agent decides

One condition (per tier): ITERATE-style loop, but the agent is given an
explicit **restart tool with scope**:
`restart(scope = file | directory | all-my-work)` — reverts the chosen slice
of its own diff (one file, every touched file under a directory, or the whole
diff) and continues. The prompt presents restart as a legitimate,
cost-free option, not a failure admission. Everything is logged per round:
tests state, decision taken, scope chosen.

Scope is a **measured variable, not a condition** (avoids matrix explosion):
does the strong tier do surgery (revert one file) while the weak one either
razes everything or never restarts? Caveat to declare: with small features
the granularity ceiling is low; greenfield tasks would be the regime where
full restarts shine — out of scope here (see gates).

## Metrics

### Phase 1
- **Primary**: pass rate per policy × tier (solved within K), paired McNemar
  per feature across policies (same stats tooling as article 1).
- **Efficiency**: rounds-to-solve and $-to-solve (a policy that wins while
  costing K× is part of the story, as in article 1's price tag).
- **Per-round test-progress curves** (the *why*): for ITERATE — monotone
  improvement vs **plateau** (≥2 rounds with no test gained) vs regression;
  plateau frequency is the key number. For RESTART — cross-attempt variance
  (lucky draw vs convergence).
- **Mechanism diagnosis**: the FRESH vs INFORMED contrast (above).

### Phase 2
- Voluntary restart **rate and timing** (after which round; after what signal
  — plateau vs single failure).
- **Scope chosen** (file/directory/all) by tier.
- **Calibration against ground truth**: Phase 1 labels each feature as
  "restart-favorable" (restart policy >> iterate on it). Do agents restart
  *more on those*? This is the honest metacognition metric — correlation of
  the decision with when restarting actually helps, not raw restart counts.
- Conditional payoff: solve-after-restart vs solve-after-persisting in
  comparable test states.

### Anti-shallow-measurement protocol (article 1 lessons, same rigor)
- TDD on the runner's pure pieces (reset policies, plateau detection, metrics)
  with the failing-test-first discipline; wiring validated with a real
  1-feature docker smoke before every batch.
- **Independent adversarial code audit before trusting Phase 1 numbers**:
  a reviewer agent hunts composition/routing bugs in the loop runner and the
  visible evaluator ($0, same as article 1 — that audit caught the c4 false
  0% and the team mis-routing). Special attention to the recurring bug class:
  *what state does each round actually apply/measure* (reset really resets,
  iterate really carries the diff, feedback really matches the round's tree).
- Any round 0%/100% cell gets audited before being believed (three false 0%s
  were caught in article 1).
- Per-round artifacts persisted (patch, test results, decision, feedback
  shown) so curves can be re-analyzed without re-spending; an
  `isolate`-style re-eval must be possible offline.

| stage | what | est. Azure | est. wall time |
|-------|------|-----------|----------------|
| 0. Pilot gate | 6 features × {ITERATE, RESTART-FRESH} × strong × K=4 | ~$7 | 1-2 h |
| 1. Policy A/B/C | full pool × 3 policies × 2 tiers × K=4 | ~$45-55 | 8-12 h |
| 2. Agent decision | full pool × decision mode × 2 tiers | ~$15-20 | 4-6 h |
| 3. Seeds | 2 extra seeds of the headline contrast | ~$20-25 | ~6 h |

**Pilot gate — does CooperBench capture the phenomenon?** (user's "whatever
works" ladder: CooperBench → SWE-bench → synthetic tasks)
- Too easy (first-round solve > ~70%): no dilemma to measure → harder pool or
  escalate.
- Too hard (0 solves even at K=4): no signal → escalate.
- Useful zone: first-round solve ~20-60% AND plateaus actually occur under
  ITERATE → proceed on CooperBench.

Before every run: report time + cost estimate split Azure/Modal (standing
user rule).

## Risks and non-claims

- **Best-of-K objection**: addressed by design (equal compute) and framing —
  see Phase 1 notes.
- **Plateau definition sensitivity**: report raw per-round curves alongside
  the ≥2-rounds threshold so readers can apply their own.
- **Ops gotchas carried over**: sleeping Mac kills runs (everything
  resumable); pallets_click task2068 saturates docker-run above c=2; redis
  lives on 6398 (6379 is taken by another project).
- We will NOT claim: anything about greenfield regimes; "agents should always
  restart/iterate"; human extrapolation beyond a nod (article 1 did that).

**Publishable in any direction** if cleanly measured: iterate wins →
"the loop needs feedback, not restarts"; restart wins → "your agent doesn't
know when to quit — make it"; capability interaction (the bet) → article 1
found capability×structure, this one hunts **capability×metacognition**, with
Phase 2 calibration as the potential headline.

## Deliverables and implementation units

- Bilingual blog article (new branch from up-to-date main; merge = publish).
- Code in the public fork, new branch `experiment/restart-loop`
  (github.com/JaviMaligno/CooperBench).
- Three isolated units, each testable alone:
  1. **Loop runner** — orchestrates rounds, applies the reset policy
     (`--policy iterate|restart-fresh|restart-informed|agent-decides`),
     resumable per feature like all our runners.
  2. **Visible evaluator** — runs the feature suite mid-loop and formats
     feedback (wraps `run_patch_test`; identical output shape for all
     policies).
  3. **Metrics aggregator** — per-round curves, plateau detection, McNemar,
     calibration; reads only persisted artifacts.

## Audit outcome (T10, pre-Phase-1 gate) — 2026-07-13

Adversarial audit (independent agent, static + empirical on pilot artifacts):
initial verdict FAIL with a solid core — 10 items VERIFIED with evidence
(cumulative composition byte-exact; a solved round's cumulative patch
re-applied and re-passed in docker via the eval's own path; fresh has zero
code/prompt leakage; informed summary strictly harness-built; agent-decides
strip feeds both the adapter and the round's eval; resume rebuilds identical
results; solved cannot be un-set; no gold-patch fallback on empty patches).
The pilot itself caught three composition bugs before this audit (missing
--recount, missing --ignore-whitespace, and last-delta-instead-of-cumulative
for iterate — the article-1 c4 class; iterate pilot data was discarded and
re-run after the fix).

Two MAJORs fixed and re-audited (PASS, commits d37fc2c + 929f07d):
1. Process-global cost cap could truncate features silently (no result.json
   → vanishing denominators, broken pairing). Now: failure result.json is
   always persisted (error surfaced, feature stays in the denominator);
   batch cap 25→60 (safety net, not a guillotine).
2. Harness-error rounds masqueraded as 0-progress (false plateaus, deflated
   pass rates). Now: round entries carry the eval error field; metrics
   exclude error rounds from curves/plateau/gate and surface an errors
   count (tests.json fallback for pre-fix artifacts; zero-round crashes
   included).

Minor backlog for analysis time: plateau-vs-regression split in the
aggregator (raw curves persisted, re-analyzable); pre-check strict-apply
mirror (round-open tolerant vs eval strict — unobserved in pilot);
partial-crash features land in plain-fail (conservative direction).

**RE-AUDIT PASS → Phase 1 launch approved.** Pilot gate: USEFUL ZONE
(first-round solve 42%, plateaus present). Early n=6 signal: iterate 5/6
vs restart-fresh 3/6 at equal compute.
